# 钉钉新品待办卡片接入说明

> 日期：2026-07-06  
> 读者：主线后端 / 前端开发  
> 用途：说明当前已经设计并验证的钉钉新品待办卡片、变量、触发逻辑和调用方式。  
> 安全边界：本文不记录 Client Secret、access token、callback secret、完整 DingTalk userId、服务器密码或任何 `.env` 值。

## 1. 当前结论

第一版只用一张通用互动卡片模板：

```text
新品待办
```

同一张模板同时服务运营和主管。后端按收件人角色传不同变量，不需要维护两套卡片，也不需要新建复杂 v2 变量。

当前使用模板：

```text
e335a9d6-72f9-495f-aafa-58cc7023d99a.schema
```

已废弃旧测试模板：

```text
33a51070-b26d-4ee8-a7d2-33deb9976b67.schema
```

图片固定在钉钉卡片模板里即可。不要再把图片做成变量；钉钉卡片图片变量通常要求 `mediaId`，普通公网图片 URL 不能稳定展示。

## 2. 卡片结构

卡片固定展示两个待办槽位：

```text
固定图片

新品待办
你有 X 项新品事项待处理

左侧事项：数量    右侧事项：数量

说明文案

[按钮]
```

第一版不在卡片里展示商品明细、不认领理由、证据图或淘汰款明细。卡片只负责提醒和入口，业务处理进入平台页面完成。

## 3. 变量清单

所有变量按字符串传入。

| 变量 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `card_title` | 是 | `新品待办` | 卡片标题 |
| `summary_text` | 是 | `你有 14 项新品事项待处理` | 总提示文案，由后端拼好 |
| `left_label` | 是 | `待认领` | 左侧事项名称 |
| `left_count` | 是 | `12` | 左侧事项数量 |
| `right_label` | 是 | `待补充` | 右侧事项名称 |
| `right_count` | 是 | `2` | 右侧事项数量 |
| `tip_text` | 是 | `请处理待认领新品和退回补充事项` | 底部说明 |
| `action_text` | 是 | `立即处理` | 按钮文案 |
| `action_url` | 是 | `https://example.com/?from=ding&role=operator` | 按钮跳转地址 |

不要在 `action_url` 里携带用户身份、token、手机号或姓名。身份由钉钉 H5 免登进入平台后识别。

## 4. 运营卡片

运营只展示两类当前要处理的事项：

```text
待认领
待补充
```

公开 Mock 数据填这个：

```json
{
  "card_title": "新品待办",
  "summary_text": "你有 14 项新品事项待处理",
  "left_label": "待认领",
  "left_count": "12",
  "right_label": "待补充",
  "right_count": "2",
  "tip_text": "请处理待认领新品和退回补充事项",
  "action_text": "立即处理",
  "action_url": "https://www.baidu.com"
}
```

触发来源：

| 场景 | 触发时机 | 统计口径 |
|---|---|---|
| 待认领 | 主管确认分配 / 改派后 | 当前运营名下待处理 `sales_claim` 任务，排除已退回补充状态，按主 SKU 去重 |
| 待补充 | 主管退回不认领补充后 | 当前运营名下 `returned_for_supplement` 的待处理 `sales_claim` 任务，按主 SKU 去重 |

`到货未处理` 是后续到货/二次调研环节，不放进当前运营卡片第一版。

## 5. 主管卡片

主管同一张模板，展示两类复核事项：

```text
认领待复核
不认领待复核
```

主管预览 Mock 数据可以填这个：

```json
{
  "card_title": "新品待办",
  "summary_text": "你有 7 项主管事项待处理",
  "left_label": "认领待复核",
  "left_count": "5",
  "right_label": "不认领待复核",
  "right_count": "2",
  "tip_text": "请按小时汇总复核运营提交的认领和不认领",
  "action_text": "进入主管处理",
  "action_url": "https://www.baidu.com"
}
```

触发来源：

| 场景 | 触发时机 | 统计口径 |
|---|---|---|
| 认领待复核 | 每小时汇总更新一次，不按单条提交即时推送 | 状态为 `待复核-认领` 的记录数 |
| 不认领待复核 | 每小时汇总更新一次，不按单条提交即时推送 | 状态为 `待复核-不认领` 的记录数 |

第一版不推送“主管待分配”，因为主管本人就是分配动作发起人。后续如果运营把商品改为 `淘汰款`，再新增主管提醒口径；当前不进入本卡片。

## 6. 后端发送规则

最小规则：

1. 后端按收件人角色计算两个数量。
2. 两个数量都为 `0` 时不发卡片。
3. 至少一个数量大于 `0` 时发送卡片。
4. `action_url` 指向平台页面，由平台页面完成钉钉 H5 免登和权限校验。
5. 运营卡片由分配、改派、退回补充等个人待办变化触发。
6. 主管卡片做小时级汇总更新，不在运营每提交一条认领/不认领时即时发送。

建议去重：

```text
receiverDingtalkUserId + role + scene + businessDate
```

状态进入型提醒仍可保留业务去重键：

```text
taskId + status + receiverDingtalkUserId
```

不要把完整 DingTalk userId 写入业务日志。需要排查时只打印前缀或 hash。

## 7. 调用方式

已验证的发送接口：

```text
POST https://api.dingtalk.com/v1.0/card/instances/createAndDeliver
```

请求头：

```text
x-acs-dingtalk-access-token: <enterprise_access_token>
Content-Type: application/json
```

获取企业 access token：

```text
POST https://api.dingtalk.com/v1.0/oauth2/accessToken
```

`appKey` / `appSecret` 从生产 secret manager 或环境变量读取，不要写入仓库。

发送 payload 形态：

```json
{
  "userId": "<receiver_dingtalk_user_id>",
  "cardTemplateId": "e335a9d6-72f9-495f-aafa-58cc7023d99a.schema",
  "outTrackId": "new-product-todo-<role>-<business-key>",
  "cardData": {
    "cardParamMap": {
      "card_title": "新品待办",
      "summary_text": "你有 14 项新品事项待处理",
      "left_label": "待认领",
      "left_count": "12",
      "right_label": "待补充",
      "right_count": "2",
      "tip_text": "请处理待认领新品和退回补充事项",
      "action_text": "立即处理",
      "action_url": "https://example.com/?from=ding&role=operator"
    }
  },
  "openSpaceId": "dtv1.card//IM_ROBOT.<receiver_dingtalk_user_id>",
  "imRobotOpenSpaceModel": {
    "supportForward": true,
    "notification": {
      "alertContent": "新品待办",
      "notificationOff": false
    }
  },
  "imRobotOpenDeliverModel": {
    "spaceType": "IM_ROBOT"
  },
  "userIdType": 1
}
```

`outTrackId` 要保证业务侧可追踪、可去重。不要包含明文手机号、姓名或 secret。

## 8. 配置来源

生产环境需要通过 secret manager / 环境变量提供：

```text
DINGTALK_CLIENT_ID
DINGTALK_CLIENT_SECRET
DINGTALK_AGENT_ID
DINGTALK_ROBOT_CODE
DINGTALK_NEW_PRODUCT_TODO_CARD_TEMPLATE_ID
```

其中：

```text
DINGTALK_NEW_PRODUCT_TODO_CARD_TEMPLATE_ID=e335a9d6-72f9-495f-aafa-58cc7023d99a.schema
```

本地 Codex 调试机已经保存过这些值，但该本地文件不属于项目运行依赖，不要复制进仓库。

## 10. 不做的事

第一版不要做：

- DingTalk Todo。
- 钉钉在线表自动写回。
- 在 URL 中携带身份。
- 为运营和主管维护两套卡片模板。
- 在卡片里展示详细商品明细、不认领理由、图片证据或淘汰款明细。
- 把后续 `到货未处理`、`淘汰款待处理`、`四周总结` 混进当前运营卡片。

这些内容进入平台页面或后续阶段处理，卡片只负责提醒和入口。
