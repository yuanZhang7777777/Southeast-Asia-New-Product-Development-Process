## 2. 三个工具各自解决什么问题

### Spec Kit

Spec Kit 解决“需求如何变成可执行规格”的问题。

本项目用它做：

- 把自然语言需求写成正式 `spec.md`。
- 对不清楚的需求做结构化澄清。
- 生成计划、任务、检查清单。
- 在实现前检查 spec / plan / tasks 是否互相矛盾。

适合阶段：

- 需求冻结。
- MVP 范围确认。
- 页面、字段、状态、验收标准定稿。
- 开发前拆任务。

不适合：

- 还没想清楚时直接生成代码。
- 替代业务人员决策。
- 把所有未来阶段一次性规划成代码任务。

### Superpowers

Superpowers 解决“AI 开发过程如何更有纪律”的问题。

本项目用它做：

- 需求讨论前先结构化澄清。
- 规划前先写清成功标准。
- 开发时用 TDD / verification 流程。
- 调试时先找根因，不乱试。
- 完成前做 review 和验收。

适合阶段：

- 需求澄清。
- 写计划。
- 调试问题。
- 做代码 review。
- 做验收前检查。

不适合：

- 代替 Spec Kit 做正式规格文件。
- 代替 Ponytail 做范围裁剪。
- 在业务还没定的时候强行进入 TDD。

### Ponytail

Ponytail 解决“不要过度设计”的问题。

本项目用它做：

- 每次写代码前先判断是否真的需要写。
- 优先复用已有代码、标准库、平台能力和已安装依赖。
- 阻止为未来功能提前建复杂框架。
- review 时检查是否改了无关文件、是否抽象过度、是否增加不必要依赖。

适合阶段：

- 裁剪 MVP 范围。
- 实现 P0 问题。
- 代码 review。
- 需求变大时判断是否后置。

不适合：

- 缩减业务需求文档的完整性。
- 省略安全、权限、数据追踪、验收。
- 用“少写代码”作为不理解业务的理由。

## 3. 本项目推荐流程

### 阶段 A：需求冻结，不写代码

目标：把第一版 MVP 到底做什么定清楚。

使用方式：

- Superpowers：用需求澄清和计划流程组织讨论。
- Spec Kit：生成或更新正式规格。
- Ponytail：把非 MVP 内容挡在后面。

推荐提示词：

```text
请进入需求冻结模式，不写代码。

请读取：
docs/00-新会话交接.md
docs/01-需求文档-东南亚新品流程.md
docs/02-功能实现状态.md
docs/05-分配任务规则设计草案.md
docs/09-MVP第一版-选品1单表跑通规格.md
docs/10-前端UX与功能测试验收清单.md
集团八部销售员信息表.xlsx

使用 Superpowers 的需求澄清/计划流程，使用 Spec Kit 的规格化方式，使用 Ponytail 的最小范围原则。

输出：
1. MVP 第一版范围冻结
2. 明确不做的范围
3. 角色和权限
4. 源表字段清单
5. 主SKU/子SKU关系
6. 商品图片、CH备注截图、不认领证据如何进入主管审核
7. 分配规则：站点 + 一级类目 + 二级类目 + 销售主攻类目
8. 每个页面必须展示的信息
9. 可备货清单 Excel 字段
10. 仍未明确、必须问业务的问题
11. 需求冻结后才能进入的下一步计划
```

通过标准：

- 业务能确认每个页面看什么、填什么、谁处理。
- 源表字段进入系统、只做快照、后置、丢弃的规则明确。
- 不认领、商品图片、CH 备注截图、主 SKU / 子 SKU 关系进入审核的规则明确。
- 可备货清单字段明确。
- 没有把采购、备货审批、供应链核价、完整钉钉上线、BI 放进第一版。

### 阶段 B：Spec Kit 规格化

目标：把冻结后的需求转成 Spec Kit 可跟踪的规格。

推荐顺序：

```text
$speckit-specify
基于已确认的 MVP 冻结结论，为“东南亚新品流程 MVP 第一版：选品1 单表跑通”创建规格。
范围只包含：源表导入 -> 新品机会池 -> 分配/自领 -> 销售认领/不认领 -> 主管审核 -> 出可备货清单 Excel。
```

如果还有模糊点：

```text
$speckit-clarify
只围绕会影响建表、流程状态、页面展示、审核证据、导出字段的问题提问。
```

生成检查清单：

```text
$speckit-checklist
为 MVP 第一版生成业务验收清单，重点覆盖源表导入、图片展示、不认领审核、搜索分页、可备货清单导出。
```

通过标准：

- 规格不包含后置阶段。
- 每条验收标准可以用页面、接口、导出文件或测试证明。
- 未确认问题单独列出，不伪装成已确认结论。

### 阶段 C：计划和任务拆分

目标：需求已冻结后，再拆实现计划。

推荐顺序：

```text
$speckit-plan
请基于已冻结 spec 生成最小实现计划，优先修 P0，禁止扩展非 MVP 功能。
```

```text
$speckit-tasks
请把计划拆成可独立验收的任务。每个任务必须说明验收路径。
```

```text
$speckit-analyze
请检查 spec、plan、tasks 是否存在范围不一致、验收缺失、任务顺序错误或隐藏的非 MVP 内容。
```

通过标准：

- 任务能按 P0 / P1 / P2 分层。
- P0 只覆盖业务试用必需问题。
- 每个 P0 都有最小验证方式。

### 阶段 D：实现和验证

目标：只实现已确认的 P0。

推荐提示词：

```text
使用 Ponytail mode 和 Superpowers verification 流程。
只修 P0，不做 P1/P2，不新增业务运行时依赖。
每修一个 P0 给出可运行验收路径。
```

实现原则：

- 先读代码和调用链，再改。
- 优先复用现有模块。
- 不新增组件库、状态库、表格库，除非现有方案无法完成 MVP。
- 非平凡逻辑至少留一个可运行检查。
- 前端改动必须用页面验证，特别是图片、搜索、分页、中文状态、不认领进入审核。

通过标准：

- P0 问题有自测结果。
- 页面能给业务试用。
- 不相关文件没有被改。
- 文档 `docs/02-功能实现状态.md` 更新实际状态。

### 阶段 E：Review 和收尾

目标：确认没有偏离需求。

推荐提示词：

```text
请使用 Superpowers code review 流程和 Ponytail review。
对照 docs/09、docs/10 和当前 spec，审计本次改动。
输出：
1. P0 是否全部闭环
2. 是否有非 MVP 功能混入
3. 是否有过度抽象或不必要依赖
4. 是否缺少验证
5. 是否需要更新文档
```

如果实现后发现任务遗漏：

```text
$speckit-converge
请对照 spec、plan、tasks 和当前代码，把仍未完成的工作追加到 tasks.md。
```

## 4. 当前项目的工具应用边界

第一版只围绕这条链路：

```text
选品1源表导入
-> 新品机会池
-> 分配/自领
-> 销售认领/不认领
-> 主管审核
-> 出可备货清单 Excel
```

第一版暂不做：

```text
采购流程
备货审批
供应链核价
复杂自动分配
完整钉钉上线
四周总结
BI 看板
```

遇到新需求时按这个判断：

| 问题 | 处理 |
|---|---|
| 不做它，销售是否无法认领？ | 是则进 MVP，否则后置 |
| 不做它，主管是否无法审核？ | 是则进 MVP，否则后置 |
| 不做它，是否无法导出可备货清单？ | 是则进 MVP，否则后置 |
| 它是否属于采购、供应链、备货审批、BI、完整钉钉上线？ | 默认后置 |
| 它是否只是让页面更漂亮但不影响判断？ | 默认后置 |

## 5. 常见场景怎么选工具

| 场景 | 用哪个工具 | 做什么 |
|---|---|---|
| 业务又提出新字段 | Ponytail + Spec Kit | 判断是否 MVP 必需；必要时更新 spec |
| 需求里有模糊点 | Spec Kit clarify + Superpowers | 只问影响实现和验收的问题 |
| 要拆开发任务 | Spec Kit plan/tasks | 生成计划和任务 |
| 要修 bug | Superpowers systematic debugging + Ponytail | 先找根因，再最小修复 |
| 要改 UI | Superpowers verification + Ponytail | 明确验收路径，不引入无关组件 |
| 要 review 代码 | Superpowers requesting-code-review + Ponytail review | 找风险、过度设计、缺测试 |
| 要开始新会话 | AGENT_HANDOFF + docs/00 + 本文档 | 恢复上下文和工作方式 |
