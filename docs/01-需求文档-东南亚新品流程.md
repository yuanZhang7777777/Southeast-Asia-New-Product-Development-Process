- 后续需要支持导出，导出结果用于外部备货汇总；导出优先，不因中央表匹配问题阻塞。
- 后续可预留通过钉钉在线表能力写回 `东南亚海外仓新品表` 对应国家站点、对应集团 / 销售员列，但中间桥第一版不作为平台闭环要求。
- 写回 `东南亚海外仓新品表` 时，目标列不按固定列号，按表头匹配，例如 `销售员1\n仔云`、`预估单销\n仔云`、`销售员2\n财根`、`预估单销\n财根`。

- 如后续启用在线表写回，主管复核完成后需要主管点击“确认写回”才执行；未启用时平台只导出。
- 周三早上主管练玉君导入系统并开始分配；新品表和财根团队新品认领截止按周四 18:00 处理。

## 1. 背景和问题

当前新品流程散在多个 Excel / 钉钉在线表 / SOP / 原型页面里。主要问题是：

- 流程节点多，容易漏处理。
- 销售、主管、开发/采购、运营之间责任边界需要明确。
- 哪些字段由系统带出、哪些字段由人填写还没有完全固定。
- 到货、缺货、广告费、1-4 周达成等异常需要及时提醒。
- 后续需求会持续变化，需要一份长期维护的项目需求文档，避免切换会话后丢失上下文。

## 2. 建设目标

第一阶段目标不是做重型 ERP，而是做一个围绕钉钉酷应用的轻流程系统：

1. 统一承接新品业务流程。
2. 每条新品机会都有状态、责任人、截止时间和处理记录。
3. 销售、主管、开发/采购、运营只看到自己该处理的任务。
4. 钉钉酷应用作为处理入口。
5. 必须处理的任务在系统内生成内部待办。
6. 钉钉只做推送和处理入口，不把第一版流程做成钉钉待办任务。
7. 所有提醒都要有去重和日志，避免重复打扰。
8. 字段、规则、责任人要能随业务讨论逐步调整。

## 3. 总体技术方案

推荐采用：

```text
钉钉在线表 / ERP / 广告平台 / 库存数据
        ↓
数据同步与规则服务
        ↓
流程实例 / 流程任务 / 字段值 / 提醒规则 / 通知日志
        ↓
钉钉酷应用页面 + 系统内部待办 + 钉钉推送
```

### 3.1 第一阶段方案

- 数据承载：先保留钉钉在线表 / Excel 作为业务数据来源。
- 流程状态：新增一套流程状态数据，不直接依赖单个在线表的颜色、筛选或人工备注。
- 后端服务：建议使用 Python FastAPI 或 Node.js 实现。
- 定时任务：定时同步在线表、ERP、库存、广告费等数据，并触发提醒规则。
- 前端入口：钉钉推送 / 酷应用入口打开平台页面；用户交互页面由平台提供，包含“我的待办”“详情页”“提交表单”“主管审核”等。
- 通知方式：
  - 行动任务：创建系统内部待办，并发送钉钉推送入口。
  - 状态通知、异常告警、日报汇总：发送钉钉推送或在系统内汇总展示。

第一阶段业务验收范围修正为：

```text
商品看板（全量状态总览） + 入池 -> 分配 -> 销售认领 -> 主管审核 -> 子 SKU 明细导出
```

备货业务执行、采购、到货、刊登、1-4 周监控和四周总结属于后续阶段。第一版只生成 `备货申请表` 和 `全字段留痕明细`，不进入采购 / 供应链待办，也不做在线表自动写回。完整端到端规划见 `docs/08-端到端流程链路规划.md`。

### 3.2 第二阶段方案

当流程和字段稳定后，再考虑：

- 把核心数据迁到 MySQL / PostgreSQL。
- 在线表只做协作视图、数据导出或报表展示。
- 增加权限模型、审计日志、规则配置页面。
- 增加 BI 看板：认领进度、备货进度、到货异常、精品成功率、缺货影响、广告投产等。

### 3.3 钉钉能力边界

当前设计依赖三类钉钉能力：

- 酷应用：作为员工在钉钉内处理流程的轻应用入口。
- 钉钉推送 / 工作通知：用于提醒、异常、汇总、升级和系统待办入口。
- 处理入口：工作通知可携带跳转链接，第一版按“直接打开任务详情页”设计。
- 身份识别：跳转链接只携带任务定位参数，不携带或信任用户身份；用户进入页面后通过钉钉 H5 免登获取当前用户身份。
- 数据写入：钉钉只做提醒和入口；用户从钉钉入口打开平台页面后提交，第一版写平台数据库，不写钉钉在线表。钉钉在线表写回作为后续能力单独实现。

实际开发前需要复核钉钉开放平台最新文档和权限申请项，尤其是工作通知 / 消息推送、用户身份、在线表读写、酷应用跳转参数。

处理入口技术口径：

1. 钉钉推送链接携带最小定位参数，例如 `taskId`、`module`、`from=ding`。
2. 酷应用页面加载后调用钉钉免登能力获取授权码，后端用授权码换取钉钉 `userId` / `unionId`。
3. 后端用钉钉用户身份映射系统用户、角色和主管关系，再按 `taskId` 查询任务。
4. 任务详情必须做权限校验：运营只能打开自己需要处理或可查看的任务；主管可打开其管理范围内任务。
5. 如果链接失效、任务不存在或无权限，页面提示原因，并回到对应模块列表。
6. 人员身份和主管关系优先从现有人员表或钉钉通讯录同步；第一版不做首次登录人工绑定。

- [工作通知能力](https://open.dingtalk.com/document/development/work-notice-option)

## 5. 主流程（两段 + 一桥）

源流程来自 `东南亚新品业务流程.xlsx`，但按运营部门视角应理解为“两段主流程 + 一座外部桥”，而非一条线性主流程：

```text
【前段·选品决策｜平台主流程·MVP】
  待认领数据(入池)
    → 主管分配（选品1 / 财根）/ 财根机会池自领
    → 销售认领（认领填单销 / 不认领填理由）
    → 主管审核（通过认领 / 确认不认领 / 退回补充）
    → 出“可备货清单”

        │  导出可备货清单 +（条件性）开品邮件状态
        ▼
【外部桥｜非平台待办，只导出 + 登记状态】
  开发备货 → 销售备货 → 供应链核价 → 采购下单 → 开船·到港·到仓

        │  到货通知回流
        ▼
【后段·到货运营｜平台主流程·后续阶段】
  到货承接(到货通知，分集团内部 / 其他集团)
    → 二次调研（外老品热销 / 老品下跌 / 销售自主）
    → 具体调整 / 竞品监控（定价、竞品、产品定位、推品准备）
    → 刊登确认（库存/售价/链接/ItemID/店铺/站点）
    → 1-4 周监控（缺货 / 广告费 / 销量表现）
    → 四周总结 → 后续动作
        ┄ 旁路：随时补货、滞销清仓
```

> 关键修正：**开发备货 / 销售备货 / 备货监控 / 采购不是平台主流程节点，而是外部桥**；平台只导出清单、登记状态、等到货通知回流。**后段第一优先级是让运营知道货到了以后该做什么**，先完成到货承接、二次调研和具体调整，再进入刊登确认。

状态模型采用两层：

- 主 SKU 组记录任务流转状态，用于机会池、分配、认领、主管复核、已驳回-待运营补充和商品看板筛选。
- 子 SKU 记录认领结果状态，用于明细展示、可备货清单和导出。
- 商品看板是第一版专门页面，用于查看所有已进入平台的商品走到哪里；它与机会池分开，机会池只展示待处理 / 可自领的新品机会。
- 如果同一主 SKU 组内部分子 SKU 认领通过、部分确认不认领，主 SKU 组显示“部分认领通过”，子 SKU 分别显示“可备货 / 已确认不认领”。
- 主 SKU 组状态先按以下中文枚举设计：待分配、待认领、待复核-认领、待复核-不认领、已驳回-待运营补充、认领通过、部分认领通过、已确认不认领、已导出可备货清单。
- 子 SKU 认领结果状态先按以下中文枚举设计：未处理、可备货、已确认不认领。
- 运营提交前的子 SKU 认领 / 不认领选择只作为当前页面表单状态，不作为正式子 SKU 状态。
- 主管确认不认领后的终态名称固定为 `已确认不认领`；第一版不允许自动重新打开或再次认领；如导出后业务需要调整，由外部导出表 / 备货流程人工处理，不回流平台。
- `已导出可备货清单` 只适用于存在认领通过子 SKU 的主 SKU 组；导出后仍保留子 SKU 认领结果。

## 6. 流程节点需求

### 6.1 待认领数据

目标：把可认领新品、老品机会、销售自主调研机会统一进入待认领池。

建议模块：`新品待认领数据池`

关键字段：

- 数据ID
- 来源类型
- 来源链接/文件
- 入池日期
- 国家/站点
- SKU / ItemID
- 产品名称 / 图片
- 类目
- 热销 / 下跌指标
- 当前状态

待确认：

- 来源类型有哪些。
- SKU 和 ItemID 哪个作为主键。
- 去重规则如何做。
- 哪些数据自动入池，哪些由人工提交。

补充要求：

- 第一版以 **子 SKU 为记录、主 SKU 为分组**。列表可以展示子 SKU 行，但详情必须能看清同一主 SKU 下有哪些子 SKU。

已确认规则：

- 工作台是唯一编辑入口；商品详情页只读展示同一主 SKU 的全部刊登、首轮第 1-4 周和后续新增周期记录，按来源业务期分组并默认展开当前业务期，不得把不同业务期记录混在一组。
- 观察区采用 Excel 式周期明细表，一行对应一个 Item 的一个业务周期；同一 Item 的全部历史周期在同一工作台按周次连续展示，填写当前周期时可直接对照过往指标、产品定位和优化操作。自动周数据只读，产品定位和优化操作可在表内直接编辑，支持勾选通过校验的记录后一键提交。横向滚动时冻结主 SKU、店铺、Item、负责人、周次和业务周期等关键列，并用连续分组样式标识同一主 SKU 的多条 Item。
- 工作台采用一张 Excel 式全量表，不再使用顶部状态分栏。业务状态作为常用筛选条件，默认值为 `待刊登`；选择 `全部` 时同时展示待刊登主 SKU 任务和全部 Item 周期记录。`待取数` 仅为系统内部取数状态，不作为运营筛选项；记录仍保留在全量表中，数据成功入库后自动进入待复盘。其他常用筛选为主 SKU / Item / 商品名称搜索、业务周期、国家、店铺文本搜索和负责人，高级筛选为周次、产品定位、跟踪状态及周期完成状态。主 SKU 作为分组层，Item 周期作为明细层。运营由权限强制只看本人记录；主管默认查看全部并可按负责人筛选。
- 四周总结不占用常驻宽列；仅第 4 周显示“填写 / 查看总结”入口，在侧边编辑区完成，并参与第 4 周提交时的必填校验。
- 刊登记录只关联主 SKU，不关联子 SKU；一个主 SKU 可以自增多个 Item。
- 系统带出并锁定主 SKU、国家、负责人等上下文。
- 每条刊登记录的必填项为 `店铺`、`Item`、自由文本 `刊登策略` 和第一周起始周期，均由运营填写或选择；店铺不接固定清单或配置模块，不再提供优化、刷单、广告、联盟、活动等固定选择项。
- 不提供脱离商品上下文的全局“新增 Item”。运营只能在 `待刊登` 列表的对应主 SKU 行内新增刊登记录；系统锁定主 SKU、国家和负责人，由运营填写店铺、Item、刊登策略和第一周起始周期。同一主 SKU 可连续新增多条“店铺 + Item”记录后统一提交。
- 运营可以填写多条 Item 后一键提交；批量提交采用整批原子规则，任意一条 Item 重复、必填项缺失或服务端校验失败时，本批全部不落库，页面保留内容并定位、标红错误行，修正后重新整批提交，不允许部分成功。每条 Item 独立选择第一周周期。
- Item 在平台内全局唯一，不按运营、平台、国家或主 SKU 划分判重范围；任何已存在 Item 再次录入时，弹窗提示既有关联并阻止提交。Item 录错允许修改；下架、换 Item 或重新刊登时，旧记录作废并保留历史，再新增新的 Item。
- 同一 `主 SKU + 国家 / 站点 + 负责人` 跨业务期再次进入待刊登时，直接展示并沿用仍有效的已有 Item，不要求重复录入；只有新店铺或新 Item 才新增记录。该场景预计很少发生，只做最小兜底，各业务期来源追溯仍独立保存。
- 已产生观察数据的刊登记录不得物理删除。
- 运营可以新增、编辑自己的记录；主管可以代录、纠错、停止跟踪或作废。
- Item 负责人由来源任务锁定，刊登创建后固定不变。业务确认不会发生负责人转交，因此不建设主管转交功能，也不设计未完成周期、提醒或后续周期的转交规则。

二次调研分流：

- 产品定位只允许 `引流款 / 利润款 / 淘汰款 / 稳定款 / 清仓款`。
- `引流款 / 利润款 / 稳定款` 进入待刊登。
- `淘汰款 / 清仓款` 不进入刊登。
- 只有淘汰款触发主管外部定位调整提醒，清仓款不通知；淘汰款不按单条即时推送，每天北京时间 `10:00` 左右汇总提醒一次。平台只负责通知主管，不接入或写回外部系统，不建设处理确认按钮、状态或待办。

### 6.12 1-4 周监控实际达成情况

目标：以 Item 为单位先完成新品上线后的四个完整业务周期，并支持运营或主管继续新增后续周期；每期自动带出周数据，由运营完成复盘。

已确认规则：

- 每个完整周期固定为周四至下周三，不按录入日期滚动计算 7 天。
- 每个 Item 独立选择第一周周期：默认下一个周期，可改选当前周期，不允许选择已经结束的历史周期。
- 刊登时只选择第 1 周起始周期；系统按有效业务周期自动生成并取数到首轮第 4 周，不等待上一周期提交。上一周期逾期未填时，下一周期仍正常生成、取数并进入待复盘。
- 同一主 SKU 后续新增 Item 时，新 Item 从自己的起始周期重新计算四周，不与已有 Item 共用周次。
- 周数据按 Item 自动获取：`订单量 <- 订单量汇总`、`总收入 <- 总收入汇总`、`一次毛利额 <- 一次毛利汇总`、`一次毛利率 = 一次毛利额 / 总收入`，毛利率按百分比展示；总收入为 0 时毛利率不可计算，页面显示 `-`，不得误显示成 `0%`。
- 正在跟踪的 Item 在某周期完全查不到周数据时，内部保持 `待取数`，不得自动按订单量、收入或毛利为 `0` 处理；系统自动重试，具体重试频率由技术设计确定。运营页面统一显示 `观察中`，四项自动指标显示 `-`，且该周期不可勾选复盘。
- 每个 Item 的每个业务周期只成功抓取一次：未查到源记录时继续重试；第一次取得有效周记录后固定订单量、总收入和一次毛利额，不再重复抓取、修订或覆盖。
- Item 是周数据的唯一值；同一周期内每个 Item 只会有一条周汇总记录，不设计多行合并逻辑。
- 首轮第 1-4 周及所有后续新增周期均由运营填写 `产品定位` 和 `优化操作`，两项都必填；每期记录独立保存，修改时保留审计记录。
- 第 1 周产品定位的未提交编辑值默认带出二次调研定位；第 2 周及后续周期默认带出该 Item 最近一个已有定位，前序周期尚无定位时回退到二次调研定位。默认带出不等于自动完成，运营仍须确认或修改后提交本周期复盘。
- 产品定位每周可变，但不会自动停止跟踪。Item 另设 `正常跟踪 / 停止跟踪`；只有明确停止跟踪后才不再取数、不再提醒。
- 某周期改为 `淘汰款` 后，Item 仍保持正常跟踪，后续周期继续生成、取数、提醒和复盘，并可在以后周期改回其他定位。第 4 周为淘汰款时四周总结仍必填；首轮完成后的第 5 周及以后仍由运营或主管手动新增。
- 观察期淘汰款主管提醒按定位变化触发，首次提交和修改已复盘记录采用同一规则：从非淘汰款改为淘汰款时提醒一次，连续保持淘汰款不重复；改为其他定位后再改回淘汰款时重新提醒。提醒事件按每天 `10:00` 左右汇总未成功通知记录。
- `停止跟踪` 后允许恢复；恢复时保留已完成的周记录，不补停止期间的数据，并从恢复后的下一个周期继续尚未完成的周次。
- 停止跟踪只阻止后续周期生成、后续取数和后续提醒；停止前已经成功取数但尚未复盘的周期仍可由负责人运营或主管正常填写并提交，不作废已取数据。
- 停止跟踪期间不生成新周期；首轮四周完成后停止自动生成，后续周期只通过运营或主管点击“新增周期”创建。
- 数据成功入库后立即给对应运营发送一次钉钉提醒；最晚在下周三下班前完成复盘，本周期不重复催促。
- 提交为“本周已复盘”后，负责人运营仍可重新打开并修改本周期人工填写的产品定位、优化操作和第 4 周四周总结，主管也可纠错；不要求额外填写修改原因，保存时继续执行相同必填校验并记录审计，周期状态保持已完成。订单量、收入、一次毛利额和一次毛利率始终只读。修改后不重新给运营发送待复盘提醒；定位由非淘汰款改为淘汰款时仍生成一次主管提醒事件。
- 商品详情按主 SKU 汇总展示多个 Item，各 Item 明细和不同周次保持独立；跨业务期历史按来源业务期分组，默认展开当前业务期。

数据接入约束：

- 复用集团八部周 Item 自动化的数据源和聚合口径，不直接依赖过滤后的成品表。
- 现有成品表会过滤 `订单量汇总 < 7`；新品观察必须按正在跟踪的 Item 定向取数且取消该门槛，不能让低销量 Item 消失，也不能改变原集团八部报表的既有口径。

### 6.13 四周总结

目标：让运营在每个 Item 的第 4 周形成一段可追溯结论。

已确认规则：

- 四周总结按 Item 单独填写，不按主 SKU 合并录入。
- 第 4 周提供必填自由文本字段 `四周总结`；主管和商品详情页可查看汇总结果。
- 同一主 SKU 后续新增 Item 时，各 Item 分别在自己的第 4 周填写总结。
- 四周总结与第 4 周产品定位、优化操作一起提交，统一截止到周数据成功入库并提醒后的下周三下班前。
- 第 4 周产品定位、优化操作和四周总结全部提交后，该 Item 进入 `首轮观察完成`。系统不自动创建第 5 周；运营或主管可以点击“新增周期”继续新增第 5 周及后续周期，序号不设上限。每个新增周期继续自动取数、发送一次提醒，并要求填写产品定位和优化操作；四周总结及所有历史周期继续保留可查看。
- `首轮观察完成` 作为 Item 里程碑保持不变；每条新增周期内部独立使用 `待取数 / 待复盘 / 已完成`。其中待取数不生成运营待办，只有数据成功入库后的待复盘周期才进入运营处理范围；不额外增加 `后续观察中` 总状态。
- 新增后续周期时默认选下一个周四至周三周期，可改选当前周期，不允许选择已经结束的历史周期。中间即使间隔数周也不自动补齐，显示周次按该 Item 实际新增记录依次编号。
- 后半段没有历史数据。2026-07-16 的新开发迁移已删除不适配 Item 级流程的旧 `four_week_summary` 表、接口和相关代码，不做兼容层或数据迁移；该删除只作用于新开发环境及代码基线，当前生产服务器和生产库未触碰。

## 7. 提醒框架

### 7.1 提醒分类

| 类型 | 用途 | 系统处理 / 钉钉触达 | 示例 |
|---|---|---|---|
| 任务型提醒 | 必须有人处理 | 系统内部待办 + 钉钉推送 | 待分配、待认领、待复核-认领、待复核-不认领、已驳回-待运营补充 |
| 异常型提醒 | 需要及时介入 | 系统标记 + 钉钉推送或系统汇总 | 逾期、缺货、到货延期 |
| 状态型提醒 | 只需要知道 | 系统汇总 + 必要时钉钉推送 | 已到货、已下单、已刊登、审核通过 |
| 复盘型提醒 | 到时间才触发 | 系统记录 / 待填写项 + 钉钉推送 | 第 7 / 14 / 21 / 28 天检查和总结 |

### 7.2 提醒设计原则

1. 能汇总就不逐条打扰。
2. 必须处理的事项建系统内部待办。
3. 需要人处理或确认的关键状态发送钉钉推送，包括待分配、待认领、待复核-认领、待复核-不认领、已驳回-待运营补充。
4. 第一版不生成钉钉待办任务，钉钉只承载推送和酷应用入口。
5. 状态进入时立即推送一次。
6. 第一版推送内容包含商品图缩略图、主 SKU、商品名称、当前状态、责任人、处理入口。
7. SLA 指每个节点允许处理的时限；具体时长暂不设默认值，待业务复核后按节点配置。
8. 超过 SLA 当天推送责任人；继续逾期后继续推送责任人，并同步推送主管。
9. 逾期扫描第一版每天 09:30 执行一次。
10. 前段按周批次截止：周三主管分配，周四运营提交，周四主管复核汇总。
11. 异常先提醒责任人，再按规则升级主管。
12. 每条提醒必须有去重 key；第一版按 `taskId + status + receiverUserId` 去重。
13. 每次提醒都写入通知日志。
14. 同一任务对同一接收人在未发生状态变化前，不重复发送相同提醒；不同接收人独立发送，适配几百人使用规模。
15. 提醒文本必须带处理入口，点击进入对应酷应用页面。
16. 处理入口默认直接打开对应任务详情页；身份由钉钉免登识别，URL 参数只用于定位任务。

### 7.3 初始提醒规则

| 触发点 | 接收人 | 方式 | 时机 | 升级 |
|---|---|---|---|---|
| 分配认领任务 | 销售 | 系统内部待办 + 钉钉推送 | 进入待认领时立即推送一次 | 超过 SLA 当天推责任人；继续逾期继续推责任人，并同步推主管 |
| 销售提交认领 | 主管 | 系统内部待办 + 钉钉推送 | 进入待复核-认领 / 待复核-不认领时立即推送一次 | 超过 SLA 当天推主管 |
| 主管退回补充 | 销售 | 系统内部待办 + 钉钉推送 | 进入已驳回-待运营补充时立即推送一次 | 超过 SLA 当天推责任人；继续逾期继续推责任人，并同步推主管 |
| 可备货清单生成 | 主管 / 数据专员 | 工作通知 | 导出后 | 后续外部桥人工跟进 |
| 预计到货延期 | 开发/采购、主管 | 工作通知 | 每日规则扫描 | 持续延期升级 |
| 到货完成 | 销售/运营 | 系统内部待办 + 钉钉推送 | 进入待二次市场调研时立即推送一次；实际入仓后 1 天内完成二次市场调研 | 超过 SLA 当天推责任人；继续逾期继续推责任人，并同步推主管 |
| 缺货 | 销售/运营 | 系统标记 + 必要时钉钉推送 | 库存低于阈值 | 持续缺货主管 |
| 首轮及后续周期复盘 | 运营 | 刊登与观察工作台 + 钉钉推送入口 | 每个周四至周三周期数据成功入库后立即推送一次 | 最晚下周三下班前提交，本周期不重复催促 |
| 第 4 周总结 | 运营 | 同一 Item 的第 4 周填写区 | 随第 4 周复盘一并展示和提交 | 最晚下周三下班前提交 |

## 9. 酷应用页面框架

第一阶段建议页面：

1. `商品看板`
   - 第一版必须保留，是完整商品状态总览。
   - 按主 SKU 分组展示所有已进入平台的商品，支持展开查看子 SKU。
   - 展示每个主 SKU / 子 SKU 当前走到哪里，包括待分配、待认领、待复核-认领、待复核-不认领、已驳回-待运营补充、认领通过、部分认领通过、已确认不认领、已导出可备货清单等状态。
   - 商品看板、运营认领页、主管复核页都通过点击主 SKU / 子 SKU 文本进入商品详情页；第一版不额外堆叠重复的 `查看详情` 按钮。
   - 商品详情页返回入口固定在页面标题旁；刷新成功等系统状态用小提示展示，不占主内容布局。
   - 默认筛选项为站点、运营、状态、健康标签、一级类目 / 二级类目、来源批次；搜索框支持主 SKU、子 SKU、商品名、关键词。
   - 后段节点如到货、二次调研、定价、刊登、每周监控、四周总结在第一版只可作为状态标签 / 占位展示，不创建后段待办。

2. `机会池`
   - 只展示待处理 / 可自领的新品机会，不代表全量商品状态。
   - `选品1` 导入后进入分配台等待主管按主 SKU 组一键分配；商品看板可全量查看，运营机会池不展示为可自领。
   - `选品2` 财根反馈表作为机会池来源，同时也参与分配台：主销售员可被分配为必处理对象，其他运营可以自领同一 SKU，人数不限。
   - 主管模式下不显示认领提交入口；只有运营身份进入机会池时才可对财根机会自领。
   - 支持按主 SKU、子 SKU、关键词、产品名称、站点、一级类目、开发员、销售员、状态搜索和筛选。

3. `源表导入页`
   - 主管通过拖拽 Excel 到上传区或点击选择文件导入选品1 / 选品2反馈表。
   - 业务 UI 不展示服务器本地路径输入，也不展示“默认表”概念。
   - 可保留 Sheet 名称输入，用于选择工作簿内具体 sheet。

4. `我的待办`
   - 按当前钉钉用户展示需要处理的任务。
   - 支持按流程节点、逾期状态、优先级筛选。
   - 节点、角色、状态全部展示中文业务名。
   - 任务行应展示商品缩略图、主 SKU / 子 SKU、站点、当前责任人和处理动作入口。

5. `任务详情`
   - 展示商品信息、来源、历史数据、当前节点、字段表单、处理记录。
   - 系统内部待办和钉钉推送入口点击后进入这里。
   - 支持查看产品图片、市场调研截图、源表行号和来源快照。

6. `分配台`
   - 给主管 / 组长使用。
   - 展示待分配数据、销售任务量、主 SKU 分组、分配建议。
   - 支持按站点、一级类目、二级类目、主 SKU、子 SKU、关键词搜索。
   - 分配建议需要展示推荐原因和可人工覆盖。
   - 默认全部启用运营参与一键分配，不让主管手工输入候选运营名单。
   - 同页提供主管可维护的运营配置表，只含销售员、重点站点、重点品类1、重点品类2和是否启用。

7. `销售认领页`
   - 给运营按主 SKU 组填写是否认领、子 SKU 认领单销、不认领原因。
   - 必须展示商品图片、开品理由、主 SKU 组和子 SKU 明细。
   - 不使用右侧统一处理面板；认领 / 不认领表单直接放在对应商品卡片内。
   - 认领只填认领单销；不认领只填不认领原因，并可粘贴、拖拽或选择调研图片证据。
   - 支持一键提交全部已填写或提交本组已填写，只提交填写完整的子 SKU。
   - 不认领时必须填写原因；提交后进入主管审核。
   - 商品卡片列表应作为独立滚动区域，顶部导航、工具条和当前运营身份不因列表滚动消失。

8. `主管审核页`
   - 给主管处理通过认领、确认不认领、退回补充。
   - 同时展示认领和不认领提交。
   - 认领提交显示 `待复核-认领 / 运营已认领`，可通过认领或退回补充；退回补充必须填写原因。
   - 不认领提交显示 `待复核-不认领 / 运营不认领`，可确认不认领或退回补充；退回补充必须填写原因。
   - 必须展示销售提交内容、源表 `CG/CH` 内容、备注截图/附件、竞品调研依据。

9. `可备货清单页（外部桥）`
   - 展示主管审核通过后可导出的新品清单。
   - 不做采购/供应链审批，只用于导出给外部流程和记录开品邮件状态。
   - 审核通过后只进入可备货清单，不自动生成 Excel。
   - 可备货清单只做子 SKU 明细导出，不做主 SKU 汇总页。
   - 同一次导出批次包含两个子 SKU 明细导出：
     - `备货申请表`：按 `海外仓备货申请表.xlsx` 的 16 列结构，用于下游备货操作。
     - `全字段留痕明细`：和 `备货申请表` 在同一个“主管复核通过后点击导出”环节生成；不是导入来源表，也不是人工填写表。行范围与本次备货导出的子 SKU 一致，字段先按 `东南亚海外仓新品表-PH/TH/VN.xlsx` 中 `开发是否接受核价结果` 前的字段，再拼接平台内部认领 / 复核 / 导出字段，用于领导查看和追溯备用。
   - `备货申请表` 中 `时间` 取系统写入 / 导出时间；`补货原因` 第一版留空。
   - 同一子 SKU 被多个运营认领通过时，按运营 / 认领任务另起多行，不合并。
   - 导出批次最小元数据为导出人、导出时间、导出文件名、导出范围。
   - 主管 / 数据人员点击导出时生成导出批次，并更新相关主 SKU 组为“已导出可备货清单”。

9. `到货提醒 / 承接页`
   - 给销售 / 运营处理到货后的二次调研入口，优先解决“货到了以后我该做什么”。

10. `二次调研与具体调整 / 竞品监控页`
   - 展示热销、下跌、竞品、库存等信号，填写调研结论、调整动作和刊登前准备。

11. `刊登与观察工作台`
   - 运营在同一页面新增主 SKU 下的多个 Item、选择各自起始周期、查看自动周数据，并填写每周产品定位、优化操作和第 4 周总结。
   - 商品详情页只读汇总主 SKU 下所有 Item，不重复提供编辑表单。

## 10. 权限原则

初步权限：

- 销售 / 运营：只能处理分配给自己或自己认领的任务，查看自己相关记录。
- 主管：第一版固定为练玉君，查看和处理分配、审核、导出及异常升级。
- 开发 / 采购：查看通过审核后进入备货的任务，维护供应和采购信息。
- 运营：查看到货、刊登、缺货、广告、推品相关任务。
- 管理员 / 数据专员：维护数据同步、人员映射、规则配置、异常修正。

配置权限：

- 人员配置表由管理员 / 数据专员维护，第一版主要维护销售员、岗位、重点站点、主攻品类。
- 类目分配配置由管理员 / 主管维护，用于声明销售主攻一级类目、二级类目、站点和启用状态。
- 第一版不依赖主管 / 组长与销售员精确归属关系；平台主管角色固定为练玉君。
- 暂不做首次登录人工绑定；钉钉身份只用于识别当前用户并映射到运营或主管角色。

待确认：

- 其他集团到货监控的数据权限。
