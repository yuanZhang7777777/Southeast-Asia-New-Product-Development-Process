# 分配任务规则设计草案

> 更新：2026-07-16
> 状态：MVP 分配规则已实现；本文记录当前代码口径和后续可选扩展。

## 1. 当前已实现的最小规则

| 规则点 | 当前实现 | 待业务确认 |
|---|---|---|
| 分组单位 | 按来源、批次、站点和 `main_sku` 聚合预览，同组子 SKU 不拆分 | 是否需要引入更细的拆组边界 |
| 负载单位 | 当前未完成主 SKU 组数 + 本次预览已分配主 SKU 组数；子 SKU 数只用于展示 | 是否需要按类目、站点、难度加权 |
| 候选人 | 全部启用运营，并按商品站点过滤 | 是否需要增加容量上限或主管范围 |
| 推荐逻辑 | 类目匹配优先；同层先按主 SKU 组负载，再按优先级、自定义顺序和姓名稳定排序 | 是否要加入历史业绩 |
| 生效方式 | 系统只预览建议，主管确认后生成运营认领任务 | 是否允许系统自动分配 |
| 改派 | 第一版不做改派；只支持分配前调整推荐人 | 后续如需要再设计审计规则 |

## 2. MVP 分配流程

```text
待分配新品机会
  -> 按来源、批次、站点和 main_sku 聚合
  -> 计算每组子 SKU 数
  -> 从启用运营中按站点筛选候选人
  -> 系统给出均衡建议
  -> 主管人工调整并确认
  -> 为运营生成认领任务
```

## 3. 会议确认清单

| 问题 | 建议默认口径 | 业务结论 |
|---|---|---|
| PH/TH/VN 是否跨站点混合分配 | 不混合，先按站点过滤候选人 | 待确认 |
| 同一主 SKU 是否必须分给同一销售 | 必须整组分配，避免子 SKU 分散 | 待确认 |
| 运营当前负载怎么统计 | 按未完成主 SKU 组数 + 当前预览草稿主 SKU 组数 | 已实现 |
| 是否考虑历史认领成功率 | 第一版不考虑，只在后台展示 | 待确认 |
| 是否考虑类目熟悉度 | 第一版不考虑，后续做规则配置 | 待确认 |
| 是否允许销售拒绝后自动转派 | 第一版不自动转派；主管确认不认领后对应子 SKU 结束 | 已确认 |
| 改派后原任务怎么处理 | 第一版不做改派 | 已确认 |
| 一条机会能否分给多个销售 | `选品1` 不允许；SKU 商品池允许多人独立认领同一主 SKU | 已确认 |
| 分配后认领 SLA | 建议 24 小时 | 待确认 |
| 逾期升级对象 | 销售本人 -> 直属主管/组长 | 待确认 |

## 4. 后续可扩展但不进 MVP 的规则

- 按站点、类目、历史业绩、当前缺货压力综合打分。
- 黑名单/白名单：某销售不接某类目或优先接某类目。
- 大主 SKU 自动拆组，但需要业务明确拆组边界。
- 批量导入人员容量，如每天最多可接几个主 SKU。
- 改派及对应审计。

## 5. 类目与人员配置底座（规划）

目标：后续让系统根据商品类目和人员关系给出更准确的分配建议，但仍保留组长人工确认。

当前口径：第一版使用“运营重点站点 + 重点品类 + 主 SKU 组负载 + 优先级 + 自定义顺序”作为分配建议依据；“组长 -> 运营”精确归属关系暂不作为第一版关键条件。

当前来源文件：`集团八部销售员信息表.xlsx`

| 字段 | 用途 |
|---|---|
| 销售员 | 分配候选人 |
| 岗位 | 区分组员 / 组长；第一版组长是否参与认领待确认 |
| 运营分层 | 可作为后续优先级或容量参考 |
| 业务类型 | 过滤精品（海外仓）业务人员 |
| 重点站点 | 站点匹配 |
| 重点品类1 | 主攻品类，优先级高 |
| 重点品类2 | 辅助主攻品类，优先级次之 |

### 5.1 一级/二级类目配置

建议维护 `category_assignment_rule`：

| 字段 | 说明 |
|---|---|
| `site` | 站点，如 PH / TH / VN |
| `category_level1` | 一级类目，来自源表 D 列 |
| `category_level2` | 二级类目，来源待确认 |
| `salesperson_name` | 主攻该类目的销售 |
| `priority` | 优先级，数值越高越优先 |
| `capacity_limit` | 可选，周期内最大待认领主 SKU 数 |
| `enabled` | 是否启用 |
| `remark` | 说明，如“只接摩配外观件” |

待确认：

- 二级类目来自源表、人工维护映射，还是后续由系统/AI 辅助归类。
- 一个类目是否允许多个销售主攻。
- 销售是否可以配置“不接某类目”的排除规则。

### 5.2 主管-销售人员配置（后续可选）

当前结论：暂时不重要，第一版不依赖“组长 -> 销售员”关系。后续如果要做审核权限隔离、逾期升级、主管工作量统计，再补充。

建议维护 `manager_sales_mapping`：

| 字段 | 说明 |
|---|---|
| `site` | 站点 |
| `manager_name` | 主管 / 组长 |
| `salesperson_name` | 销售 / 运营 |
| `team_name` | 小组 |
| `enabled` | 是否启用 |
| `effective_from` / `effective_to` | 生效时间，可选 |

规则：

- 第一版不按主管范围过滤候选销售，先按站点、主攻品类、负载推荐。
- 后续如启用主管范围，主管只能分配、审核自己配置范围内的销售任务，除非管理员授权跨组处理。
- 人员配置变更要保留历史，历史任务不因人员表变化而丢失责任人。

### 5.3 分配建议评分顺序

建议优先级：

1. 站点过滤：只在同站点的启用运营中推荐。
2. 类目匹配：商品一级类目命中 `重点品类1` 或 `重点品类2` 均进入同一匹配层；未命中者进入下一层。
3. 当前负载：同一匹配层内，未完成及本次预览的主 SKU 组数越少越优先；子 SKU 数不参与第一版均衡排序。
4. 人员优先级：负载相同时，`assignment_priority` 数值越高越优先。
5. 自定义顺序：前述条件相同时，按站点内 `display_order` 和运营姓名稳定排序。
6. 人工覆盖：主管可以在确认前手动指定推荐人，第一版不要求填写改派原因。
7. 主管范围匹配：后续可选项，不进入第一版必要规则。

选品1源表 `CD` 主销售员仅保留原值追溯，不进入推荐评分。

分配台必须展示推荐原因，例如：

```text
推荐给 张三：TH 站点匹配；重点品类=汽配与摩配；当前待认领 3 个主 SKU 组。
```

### 5.4 站点内展示顺序

- 分配台按标准化站点分组展示运营，并按 `display_order` 排列。
- 运营配置抽屉支持拖拽和上下按钮；拖拽只允许在同站点内调整，跨站点拖拽不生效。
- 排序只是本地编辑，必须点击“保存运营配置”后才持久化。
- 分配过程中，运营负载横条固定在分配列表顶部；当前草稿分配完成后，卡片中的“本次”及合计组数立即更新。

## 6. 当前代码对应

- 分配预览：`POST /assignments/preview`
- 确认分配：`POST /assignments/confirm`
- 改派任务：第一版产品不暴露改派入口；现有接口如保留，不能出现在原型和 MVP 主流程。
- 核心逻辑：`backend/app/services.py`
- 前端入口：`frontend/src/App.tsx` 的 `分配台`
