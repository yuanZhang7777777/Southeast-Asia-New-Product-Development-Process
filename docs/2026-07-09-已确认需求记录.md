## 分配台推荐规则

- 先按站点硬隔离：PH/TH/VN 等站点不混分，不属于该站点的运营不能接该站点 SKU。
- 同一主 SKU 在同一来源、同一期、同一站点内整组分配；同一主 SKU 跨站点时按站点拆开，各站点单独推荐。
- 重点品类1和重点品类2优先级相同，只要命中任一重点品类，就进入同一优先级池。
- 负载均衡按“主 SKU 组数”计算，不按子 SKU 数量计算；一个主 SKU 下有多个子 SKU 也只算 1 组负载。
- 推荐时要计入数据库里已经分配但未完成的认领任务，按“负责人 + 来源 + 期数 + 主 SKU + 站点”去重统计当前负载。
- 在同站点候选人中优先推荐当前主 SKU 组负载更少的人；重点品类命中、人员优先级和自定义顺序仅处理同负载并列。例如 A 已分配 3 个主 SKU，新任务在 A/B/C/D 都可接时，即使 A 命中重点品类或优先级最高，也应先分给负载更低的人。
- 同站点候选人初始负载相同时，单位主 SKU 组的一轮推荐结果最大相差 1 组；提高某人的 `assignment_priority` 不能让其独占同类任务。

## 运营认领与不认领

- 运营按子 SKU 选择认领或不认领；认领必须填写认领单销，不认领必须填写原因。
- 不认领原因允许单选、多选并同时填写自定义内容；保存时按下列固定顺序，以中文分号 `；` 连接，历史自定义文本不得丢失：
  1. 稳定期利润率过低
  2. 产品生命周期过短
  3. 市场需求量过小
  4. 调研数据不真实
  5. 侵权/违规风险过高
  6. 产品需认证资质
  7. 抛货/重货/易碎品
  8. 系统已有同款
  9. 竞对销量差
  10. 之前卖过类似款无销量
  11. 市场竞对过多，优势不明显
  12. 系统类似款成本更低
  13. 近期销量下跌
  14. 属性价差超5倍
  15. 老链接垄断，同类型产品市场竞争大
- 运营提交后不能自行撤回；主管只能通过、确认不认领或退回补充，不能代改运营提交的认领单销或不认领原因。

- 二次调研表格底部固定展示草稿保存状态和“提交本主 SKU”按钮；整组提交结果按各子 SKU 产品定位独立分流。
- 多人认领时，当前运营编辑自己的二次调研记录，并可从对应子 SKU 行查看其他运营的二次调研记录；其他运营记录在当前运营页面中只读，不允许相互覆盖。
- 每周导入的一期数据必须在认领、复核、到货承接、二次调研等各阶段持续保留期数并相互隔离；相同主 SKU 或子 SKU 出现在不同期时，不得在页面或任务中合并成同一期记录。
- 选品1导入必须拆分“数据 Sheet”和“业务期数”两个概念：主管先选择实际读取数据的 Excel Sheet；业务期数可以直接采用该 Sheet 名称，也可以另行填写自定义名称。
- 自定义业务期数只作为贯穿认领、复核、到货承接、二次调研等阶段的期数标签，不改变实际读取的 Excel Sheet，也不改变源表追溯信息。
- 相同数据 Sheet、相同业务期数再次导入时，默认采用增量更新，不做全量覆盖：已存在的 SKU 更新字段，新 SKU 追加，本次文件中缺失的旧 SKU 继续保留，不自动删除或停用。
- 增量更新使用 `来源 + 业务期数 + 站点 + 主 SKU + 子 SKU` 判断同一条业务数据；Excel 行号只用于来源追溯，不参与重复判断。
- 同一期 SKU 重新导入时，只更新该业务记录的源表字段；已经产生的分配、认领、复核、到货承接、二次调研等流程数据和当前进度全部保留，不因重新导入而重置。
- 需要移除数据时，由有数据管理权限的人员单独停用 SKU 或停用整期数据；每次导入仍保留独立快照和审计记录。
- 系统内商品触发到货通知后，要保存该商品本次识别到货的日期和时间，作为后续二次调研的数据留痕。
- 仅下载“前一天最后一次入库”的 PLM 增量数据会漏掉系统接入前已经有库存的商品：这类商品不应继续停留在待到货，选品2中较常见。
- 后续需要对系统内符合后续资格的商品执行一次 PLM 全量库存匹配，用来识别接入前已经有货的商品；全量匹配的切入时点、去重和首次提醒策略仍待确认。
- 当前开发优先完成选品1的整套流程。选品2及其历史库存全量匹配问题先保留记录、暂缓实施，待选品1流程稳定后再继续。
- 当前实现把 `source_sheet` 同时当作数据 Sheet 和业务期数使用，必须修正为分别保存真实数据 Sheet 与业务期数，避免自定义期数导致读取错误或来源追溯失真。

## 钉钉汇总通知节奏（2026-07-13）

- 淘汰款不按单条提交即时推送。系统每天北京时间 `10:00` 左右汇总发送一次，扫描所有尚未成功通知的淘汰款记录，避免因周末、任务失败或重试造成漏发。
- 淘汰款汇总按运营、业务期数和主 SKU 组织明细；每次汇总中，每位已启用的主管和超级管理员最多接收一张卡片。没有新增未通知记录时不发送空卡片。
- 淘汰款卡片发送成功后必须记录发送时间或发送批次；定时任务重试时不得重复发送已经成功通知的记录，发送失败的记录保留到下一次重试或汇总继续发送。
- 平台对淘汰款只负责通知主管：不调用、不写回任何外部系统，不新增“外部定位已处理”按钮、状态或待办，也不保存主管在外部系统中的处理结果。钉钉通知发送成功即完成平台责任，发送失败继续按既有规则重试。
- 认领与不认领提交均不按运营每次提交即时通知主管。系统每周四北京时间 `09:00` 向已启用的主管和超级管理员发送一张复核汇总卡片，展示当前待复核认领数和待复核不认领数，并进入主管复核页处理。
- 周四汇总卡片只提供当时的数量摘要和处理入口；主管进入复核页后查看实时队列，因此汇总发送后新增的待复核记录仍会正常显示和处理。
- 主管退回补充属于明确需要原运营及时处理的动作，仍在退回发生后即时通知对应运营，不等待周汇总。
- 当前仍处于测试阶段；以上定时规则只作为正式启用后的发送口径，在业务明确确认正式启用前不得向真实人员发送卡片。

## 刊登与 1-4 周观察（2026-07-16）

### 已确认业务口径

- 新建独立的“刊登与观察工作台”，供运营查看本人全部记录并统一新增、提交和编辑，主管可查看全部运营并筛选；商品详情页只读汇总展示，不重复建设编辑表单。
- 商品详情页只读展示同一主 SKU 的全部刊登与观察历史，按来源业务期明确分组并默认展开当前业务期；不同业务期不得混成同一组。
- 2026-07-21 开发 UAT 后，观察记录从 15 列 Excel 宽表改为 `主 SKU -> Item -> 周记录` 分组卡片表格。每条周记录仍对应一个 Item 的一个业务周期，支持填写产品定位和优化操作并勾选提交；宽屏保持网格对齐，空间不足时自动换行，不用横向宽表或过窄输入框换取紧凑。
- 工作台不使用顶部状态分栏。业务状态作为常用筛选条件，默认值为 `待刊登`；选择 `全部` 时展示权限范围内的待刊登任务、已有 Item 和可见周期记录。标题、筛选、结果数量和“提交选中周记录（N）”组成固定区，只有下方结果区纵向滚动。常用筛选为主 SKU / Item / 商品名称搜索、业务周期、国家、店铺文本搜索和负责人，高级筛选为周次、产品定位、跟踪状态及周期完成状态。运营由权限强制只看本人记录；主管默认查看全部并可按负责人筛选。
- 主 SKU 折叠按钮控制该组已有 Item、刊登录入区和周期记录；收起后只保留组级摘要。主 SKU 行不重复展开内容中的国家、负责人等字段；已有 Item 使用紧凑摘要，纠错、停止/恢复和作废收进更多菜单，新增或纠错表单仅在点击后出现。
- 四周总结不作为常驻宽列；仅第 4 周提供“填写 / 查看总结”入口，在侧边编辑区完成，并参与第 4 周批量提交前的必填校验。
- 刊登记录关联主 SKU，不关联或选择子 SKU。一个主 SKU 可以新增多个 Item；每个 Item 是独立刊登记录、独立选择起始周期、独立计算四周并独立填写总结。
- 工作台由系统带出并锁定主 SKU、国家、负责人等上下文。每条刊登记录的必填项为 `店铺`、`Item`、自由文本 `刊登策略` 和第一周起始周期，均由运营填写或选择；店铺不接固定清单或配置模块，不再提供优化、刷单、广告、联盟、活动等固定选项。
- 不提供脱离商品上下文的全局“新增 Item”。运营只能在 `待刊登` 列表的对应主 SKU 行内新增刊登记录；系统锁定该主 SKU、国家和负责人，运营填写店铺、Item、刊登策略和第一周起始周期。同一主 SKU 可连续新增多条“店铺 + Item”记录后统一提交。
- 运营可以一次填写多条 Item 后一键提交。批量提交采用整批原子规则：任意一条存在 Item 重复、必填项缺失或服务端校验失败，本批所有记录都不落库；页面保留已填内容并定位、标红具体错误行，修正后重新整批提交，不允许部分成功。当前运营可以新增和编辑自己的记录；主管可以代录、纠错、停止跟踪或作废。
- Item 负责人由来源任务锁定，刊登创建后固定不变。业务确认不会发生负责人转交，因此平台不提供主管转交入口或接口，也不设计未完成周期、待发送提醒和后续新增周期的转交逻辑。
- Item 在平台内全局唯一，不按运营、平台、国家或主 SKU 划分判重范围。任何已存在的 Item 再次录入时，弹窗提示既有关联记录并阻止提交。Item 单纯录错时允许修改；真正下架、换 Item 或重新刊登时，旧记录作废并保留历史，再新增新的 Item。已经产生观察数据的记录不得物理删除。
- 同一 `主 SKU + 国家 / 站点 + 负责人` 在新业务期再次进入待刊登时，作为低频兜底直接展示并沿用仍有效的已有 Item，不要求重复录入，也不复制一份刊登记录；只有确实新增店铺或新 Item 时才新增记录。不同业务期的来源追溯仍分别保留。
- 周数据同样以 Item 为唯一值；同一周期内每个 Item 只会有一条周汇总记录，不需要设计多行校验或合并规则。
- 产品定位固定为 `引流款 / 利润款 / 淘汰款 / 稳定款 / 清仓款`，首轮第 1-4 周及所有后续新增周期均可重新选择且每期必填。
- 同一 Item 的过往周期记录全部保留在同一工作台中并按周次连续展示，运营填写当前周期时可直接查看以前的自动指标、产品定位和优化操作。
- 第 1 周产品定位默认带出二次调研定位；第 2 周及后续周期默认带出该 Item 最近一个已有定位，前序周期尚未填写时回退到二次调研定位。该默认值只用于未提交编辑，运营仍须确认或修改并提交，不能视为系统自动复盘。
- 刊登行和周期复盘的未提交内容自动保存在当前浏览器本地，并按登录用户及任务 / 周期标识隔离；刷新或误关页面后恢复，提交成功后清除对应草稿。第一版不新增服务端草稿表或草稿接口，也不做跨设备同步。
- 产品定位与 Item 跟踪状态分开。定位改为淘汰款或清仓款不会自动停止取数；只有运营或主管明确把 Item 改为 `停止跟踪`，后续才不再取数、不再提醒。
- 观察期某一周期改为 `淘汰款` 后，Item 仍保持正常跟踪：后续周期继续生成和取数，数据入库后继续提醒运营，运营继续填写产品定位和优化操作；后续任一周期可以再改为五种定位中的其他定位。第 4 周改为淘汰款时，四周总结仍照常必填；首轮完成后的后续周期仍沿用已经确认的人工“新增周期”规则。
- 观察期淘汰款主管提醒按“定位变化事件”生成，首次提交和修改已复盘记录采用同一规则：Item 从非淘汰款改为淘汰款时提醒一次；连续多个周期保持淘汰款不重复提醒；改成其他定位后再次改回淘汰款时重新提醒一次。每个变化事件进入每天 `10:00` 左右的未成功通知汇总，发送失败继续重试，发送成功后不重复。
- `停止跟踪` 后允许恢复。恢复时保留已经完成的周记录，不补停止期间的数据，从恢复后的下一个周期继续尚未完成的周次；例如已完成第 1 周后停止，恢复后继续第 2 周。
- `停止跟踪` 只影响停止后的新周期生成、周数据获取和提醒。停止前已经成功取数但尚未复盘的周期仍保留为可处理记录，负责人运营或主管可以继续填写并提交；已经取到的数据不因停止而作废。
- 首轮第 1-4 周及所有后续新增周期均人工填写 `产品定位` 和 `优化操作`，两项必填。提交为“本周已复盘”后不锁定，负责人运营仍可直接修改本人周期的产品定位、优化操作和第 4 周四周总结，主管也可纠错；无需单独填写修改原因，重新保存时沿用原必填校验、周期保持已完成并保留审计，不覆盖其他周期。自动抓取的订单量、收入和毛利字段始终只读。修改已复盘记录不重新给运营发送待复盘提醒；若定位由非淘汰款改为淘汰款，仍生成一次主管定位变化事件。
- 第 4 周增加 Item 级 `四周总结` 自由文本填写区；同一主 SKU 后续新增的 Item 仍按自己的起始周期独立观察四周。
- 四周总结与第 4 周产品定位、优化操作一起提交，统一截止到周数据成功入库并提醒后的下周三下班前。
- 第 4 周的产品定位、优化操作和四周总结全部提交后，该 Item 进入 `首轮观察完成`。系统不自动创建第 5 周；运营或主管可以点击“新增周期”继续创建第 5 周及后续周期，周期序号不设上限。每个新增周期继续自动取数、发送一次提醒，并要求填写产品定位和优化操作；首轮四周总结和全部历史周期继续保留可查。
- `首轮观察完成` 是 Item 的持久里程碑，新增后续周期时不反复修改 Item 总状态。每条周期记录内部独立使用 `待取数 -> 待复盘 -> 已完成`；待取数不生成运营待办，数据成功入库后才进入待复盘，不新增 `后续观察中` 总状态。
- 新增后续周期时默认选择下一个周四至周三周期，可改选当前周期，不允许选择已经结束的历史周期。中间即使间隔数周也不自动补齐空档，显示周次按该 Item 实际新增记录依次编号为第 5、6 周等。
- 每个完整周期为周四至下周三。周期结束后自动获取数据，成功入库后立即向对应运营发送一次钉钉提醒；运营最晚在下周三下班前完成复盘，本周期不重复催促。
- 每个 Item 的每个业务周期只成功抓取一次周数据。源数据中没有该 Item 时保持待取数并继续重试；第一次取得有效源记录并写入后，订单量、总收入和一次毛利额即固定，不再重新抓取、修订或覆盖。
- 刊登时只选择第 1 周起始周期；系统随后按有效业务周期自动生成并取数至首轮第 4 周，不等待上一周期是否已提交复盘。上一周期逾期未填时，下一周期仍正常进入 `待复盘`，工作台可以同时显示多个未完成周期。
- `停止跟踪` 期间暂停后续周期生成、后续取数和后续提醒，但停止前已成功取数的待复盘周期仍可完成；恢复后从下一个业务周期继续首轮尚未完成的周次，不补停用期间。首轮四周全部完成后停止自动生成，后续只通过运营或主管的“新增周期”创建。
- 周数据自动映射：`订单量 <- 订单量汇总`、`总收入 <- 总收入汇总`、`一次毛利额 <- 一次毛利汇总`、`一次毛利率 = 一次毛利汇总 / 总收入汇总`，一次毛利率按百分比展示；总收入为 0 时毛利率不可计算，页面显示 `-`，不得误显示为 `0%`。
- 正在跟踪的 Item 在某周期完全查不到周数据时，不得把订单量、收入和毛利自动记为 `0`；内部保持 `待取数` 并自动重试。未来尚未开始的周期不展示；当前进行中的周期只显示“第 N 周进行中、周期范围、预计取数日期”的紧凑提示，不显示空指标和复盘输入。周期结束仍未成功取数时提示“数据准备中”，成功入库后才显示完整周记录并允许提交。自动重试频率属于技术设计，不在本轮业务口径中预设。
- 现有集团八部周 Item 成品会过滤 `订单量汇总 < 7` 的记录，不能直接作为新品观察的最终输入；平台接入需复用同一数据源和聚合口径，对正在跟踪的 Item 做不带该门槛的定向取数，避免低销量新品消失。现有集团八部报表流程不因此改口径。

## 销售自选与备货申请（2026-07-21）

- 销售自选商品的海外仓库存由运营自行到公司现有系统查看，平台本期不自动查询库存，也不替运营判断是否需要新增备货。
- 只有运营确认海外仓已有可用库存时，选择“不备货”才跳过备货申请、待到货和二次调研，直接进入 `待刊登`。
- 海外仓无可用库存且选择不备货时，状态设为 `暂不推进`，不生成备货申请、待到货、二次调研或待刊登任务；保留记录和已填内容，运营后续改为备货时按正常备货链路继续。
- “已有可用库存”和“需要新增备货”互斥，页面和 API 都必须拒绝两者同时为真的矛盾组合。
- 备货仓库为可选自由文本，不提供默认值或建议值；运营可填写，也可留空提交，主管在导出的外部表中补填。
- 运营提交备货申请后直接进入主管导出中心，不新增独立主管审核页面；主管选择并导出即视为确认。
- 选品2同一子 SKU 被多个运营认领通过时，按“销售员 + 子 SKU”分别生成备货申请行，不合并；各运营的申请互不覆盖。
- 选品1/2成本价由系统从来源表自动带出，运营提交前可修改；销售自选成本价由运营手工必填。货值计算和导出均使用最终提交值，来源表原成本价继续保留在来源快照中。
- `备货数量 = 备货单销 × 30`；结果出现小数时统一向上取整为整数件。
- 单个体积优先通过 ERP 子 SKU 产品列表计算；ERP 包装尺寸和产品尺寸都不完整时，由运营填写长、宽、高（cm），三维均大于 0 后由系统自动换算单个体积（m³），运营不直接手填 m³；草稿允许暂缺尺寸且不沿用来源表“包装后体积”静默预填，正式提交前必须得到有效体积。
- 备货类型为“首次备货”时补货原因可留空；备货类型为“补货”时补货原因必填。
- 一次销售自选创建一个主 SKU 和一个或多个子 SKU，逐子 SKU 独立决定库存与备货分支；系统按北京时间创建日期生成 `销售自选YYYYMMDD` 业务期标签。
- 草稿可以反复保存；已提交但尚未导出的申请允许原运营修改并再次提交，主管始终导出最新提交值。导出成功后申请只读；导出文件生成或整批校验失败时不得推进申请或负责人状态。
- 备货草稿有修改且焦点离开当前申请编辑区时自动保存，同一申请的连续保存必须按顺序执行；无修改时不发请求，服务端收到字段相同的更新也不得把已提交申请退回草稿。同时保留“保存草稿”按钮作为显式反馈；导出后仍保持只读。
- 备货列表固定按主 SKU、子 SKU 排序；切换“需要备货 / 有库存不备货 / 无库存不备货”只能改变当前条目内容，不得因更新时间改变条目位置。
- 主管复核打开右侧复核区时，左侧标签、筛选、批量操作和卡片不得被右栏高度拉伸或改变定位，复核页不再叠加通用主管统计侧栏。

### 正式备货申请 16 列

| 列 | 字段 | 已确认规则 |
|---|---|---|
| A | 操作状态 | 平台首次导出留空，供外部流程处理 |
| B | 申请日期 | 必填，默认北京时间当天，运营可修改；导出仅写日期 |
| C | 备货类型 | 必填：首次备货 / 补货，默认首次备货 |
| D | 选品数据源 | 系统生成：选品1、选品2/财根、销售自选 |
| E | 销售员 | 服务端从登录身份和负责人记录确定，客户端不可伪造 |
| F | 主 SKU | 选品1/2来源带出；销售自选手填 |
| G | 子 SKU | 每个子 SKU 单独一行；销售自选同组不可重复 |
| H | 成本价 | 必须大于 0；选品1/2预填后可改，销售自选手填 |
| I | 单个体积 | 系统生成且必须大于 0；优先 ERP 计算，失败或缺尺寸时由运营填写长宽高（cm）后自动换算 |
| J | 备货单销 | 必须大于 0，运营填写 |
| K | 备货数量 | 服务端计算 `ceil(备货单销 × 30)` |
| L | 备货国家 | 必填；默认来源国家/站点，运营确认或修改 |
| M | 备货仓库 | 可选自由文本，可留空并由主管在外部表补填 |
| N | 货值 | 服务端计算 `最终成本价 × 备货数量` |
| O | 体积 | 服务端计算 `单个体积 × 备货数量` |
| P | 补货原因 | 补货时必填；首次备货时可空 |

### ERP 单个体积边界

- ERP 登录使用现行 Open Login 获取临时令牌；业务接口使用 `Authorization: <accessToken>`，不加 `Bearer`，不使用 Cookie 或历史固定 token。
- 包装后三维全部有效时使用包装尺寸；任一维度无效时整组回退到产品三维，禁止两组混用。两组都不完整时返回手填降级。
- `单个体积(m³) = 长(cm) × 宽(cm) × 高(cm) ÷ 1,000,000`；零、负数和非数字无效。
- ERP 未配置、请求失败或无有效尺寸时不阻止保存草稿，但正式提交前必须补全大于 0 的长宽高并由系统算出单个体积；不得用来源表“包装后体积”冒充 ERP 结果。
