发布采用候选容器健康检查后原子重载 Caddy 的方式。发布时不重启 PostgreSQL、Redis、worker 或 scheduler，旧版本容器保留用于快速回滚；`deploy/Caddyfile` 必须同步持久化到当前容器名，避免服务器重启后回退。

注意：`deploy/Caddyfile` 是只读 bind mount。宿主机使用 `sed -i`、覆盖复制等会替换 inode 的操作后，运行中的 Caddy 容器可能仍看到旧文件。无重启切流时应把宿主机持久配置通过标准输入加载，并从 Caddy Admin API 回读实际 upstream；不能只检查宿主机文件：

```bash
docker exec -i hengzhe-new-product-reverse-proxy-1 \
  caddy validate --config - --adapter caddyfile < deploy/Caddyfile
docker exec -i hengzhe-new-product-reverse-proxy-1 \
  caddy reload --config - --adapter caddyfile < deploy/Caddyfile
docker exec hengzhe-new-product-reverse-proxy-1 \
  wget -qO- http://127.0.0.1:2019/config/
```

## 6. 开发部署流程

发布包、备份和回滚目录位于 `/opt/hengzhe-new-product-dev`；所有 `docker compose` 命令必须在 `/opt/hengzhe-new-product-dev/app` 下执行：

1. 确认目标是 `hz-new-product-dev`，不要连接生产服务器。
2. 对开发 PostgreSQL 执行带时间戳的 `pg_dump`，写入 `backups/`。
3. 上传不含 `.env`、测试数据库、缓存、`node_modules` 和私密源表的发布包。
4. 保留服务器现有 `.env`；发布包不得覆盖它。
5. 运行 `docker compose config`，确认项目名和 `18081` 映射。
6. 执行 `docker compose build` 和 `docker compose up -d`；`migrate` 只升级开发库。
7. 检查迁移版本、容器健康、API 健康、首页和关键接口。
8. 写入 `DEPLOYED_COMMIT`，并保留发布包和数据库备份用于回滚。

迁移 `a8d4e6f7b901` 会在开发库创建 `listing_record`、`item_observation_period`，并删除无数据的旧 `four_week_summary`。不得把这条迁移直接用于当前生产库。

## 7. 回滚

应用代码回滚优先使用 `releases/` 中上一份发布包，并保留当前 `.env` 和 Docker volumes。数据库结构回滚前必须再次备份；若新表已经出现真实业务数据，不得直接执行 Alembic downgrade，应先评估并导出数据。

## 8. 安全与备份

- `.env` 永不入库，发布包不得包含 `.env`。
- 开发环境每次迁移前先备份 PostgreSQL。
- 上传文件和数据库卷不随代码目录替换。
- 外网只开放必要的 SSH 与 `18081`；数据库、Redis、worker、scheduler 不直接暴露。
- 日志不得记录含 Token 的完整访问 URL。
- 生产服务器在用户使用期间绝不重启。
- 2026-07-17 已在生产和开发各自的 `.env` 保存 PLM 接口配置与业务账号凭据；两边 `PLM_SYNC_ENABLED=false`，本次未重启或重建服务。实际凭据不写入仓库、文档或日志。
- 独立服务 `caigen-arrival-notifier` 与新品流程生产环境共同运行在 `101.132.26.138`，但新品流程生产环境本身不发送到货卡；到货卡由 `caigen-arrival-notifier` 单独发送。新品流程开发环境运行在 `139.224.2.166:18081`。开发期不配置该通知服务向开发库常驻写入，开发平台只做手动 PLM 验收且不自动发卡；正式平台上线后，才在批准的维护窗口切换数据同步目标和卡片按钮地址。
