# 前半段生产稳定性修复设计

> Status: approved
> Date: 2026-07-15 Asia/Shanghai

## 1. 目标

修复当前生产环境导入漏子 SKU、认领单销不可见、复核前无法修改、分配筛选和运营排序不便等问题。保持现有数据库表和业务状态模型，不引入新依赖，不中断正在填写的用户。

## 2. 已确认口径

- 分配筛选中的“销售员”指运营。
- 所有用户可见文案统一为“认领单销”；现有内部字段 `claim_daily_sales` 保持不变。
- 运营认领台默认展示最新一次导入的有效业务期数，并可切换历史期数。
- 运营提交认领或不认领后，在主管首次完成复核前可以继续修改；复核完成后只读。
- 运营认领台和商品看板同时展示未操作、已认领待复核、不认领待复核和退回补充状态。
- 同一搜索框内以空格分隔的多个关键词按任一关键词命中；站点、一级类目、运营和关键词筛选之间按同时满足处理。
- 运营默认按站点分组；同站点内使用现有 `display_order` 自定义顺序，界面提供上移/下移按钮。
- 五组竞品使用固定但克制的颜色标签和浅色列背景，并保留明确文字标签，不能只依赖颜色表达含义。

## 3. 已定位根因

### 3.1 导入漏数

选品 1 导入器把整行任意字段中出现“合计”都视为汇总行。生产源表 `开发新品0714期` 的第 126、129 行在开品理由中包含“多家竞对店铺月销合计”，因此合法子 SKU `BGQHG7801`、`BGQHG7901` 被跳过。

修复后汇总行判断只检查身份/标题单元格的精确汇总标记，不扫描开品理由等业务文本。生产补数验收为：

- `BGQHG78` 包含 `BGQHG7801`、`BGQHG7802`、`BGQHG7803`。
- `BGQHG79` 包含 `BGQHG7901`、`BGQHG7902`。

### 3.2 上传源表未持久化

代码将源表保存到 `backend/app/.private_uploads`，Compose 挂载的是 `backend/.private_uploads` 对应容器 `/app/.private_uploads`。生产源表因此落在 API 容器可写层，容器替换后可能丢失。

修复使用项目后端根目录下的 `.private_uploads/source-workbooks`，与现有 Compose 卷保持一致。上线前先把旧容器中的历史源表复制到持久卷并核对文件数量和哈希。

### 3.3 前端分组范围不足

前端当前只按“来源类型 + 主 SKU”分组，会把不同业务期数或站点的同主 SKU 混在一起。统一改为“来源类型 + 业务期数 + 标准化站点 + 主 SKU”，与后端分配规则一致。

## 4. 第一批：数据正确性与运营流程

### 4.1 导入与持久化

- 收紧汇总行判断并增加真实文本回归样例。
- 修正上传目录到现有持久卷。
- 不修改已有机会状态、平台认领、主管复核或审计历史。
- 在开发环境使用生产源表副本验证重导结果后，生产备份并执行幂等重导补数。

### 4.2 认领单销字段

- `OpportunityRead` 增加计算展示字段 `latest_claim_daily_sales`，从最新平台认领记录读取，不新增数据库列。
- 主管复核列表、运营认领列表、商品详情“认领与复核”、商品看板子 SKU 责任明细均展示认领单销。
- 商品看板主行增加“已分配运营”，多个运营用顿号连接，无负责人显示 `-`。

### 4.3 复核前修改

- 复用现有 `POST /claims` 和同一条平台认领记录。
- 普通分配任务允许所属运营在机会状态为 `claim_submitted` 或 `claim_rejected` 且尚无主管复核记录时更新。
- 更新时不创建重复主管复核任务；保留 `first_submitted_at`，更新 `last_updated_at` 并写审计。
- `/tasks/my` 返回本人仍可编辑的已提交认领任务，使认领台能继续展示这些商品。
- 前端用最新认领结果、单销、不认领原因和调研结论初始化编辑值；主管复核后不再进入可编辑列表。

### 4.4 期数与状态筛选

- 运营认领台提供业务期数和操作状态筛选。
- 最新期数以可见记录中 `created_at` 最新的有效业务期数为准，不按期数字符串猜日期。
- 状态包含全部、待填写、已认领待复核、不认领待复核、退回补充。

## 5. 第二批：分配和竞品展示

### 5.1 竞品区分

- 最低价、月销最高、月销次高、月销第三高、新晋五组分别使用固定样式。
- 运营矩阵按对应列组着色；商品详情竞品表对“竞品位置”使用同一组颜色。
- 链接按钮继续显示短域名和外链图标，不恢复完整长 URL。

### 5.2 分配筛选

- 增加站点下拉、一级类目下拉、运营下拉和多关键词输入。
- 运营筛选匹配系统推荐或主管当前手动选择的最终运营。
- 多关键词匹配主 SKU、子 SKU、主/子商品名；空格分词后任一命中。
- 条件变化时回到第一页，不改变已选择的分配草稿。

### 5.3 运营排序

- 工作量卡片、最终分配下拉和人员配置表均按标准化站点分组。
- 站点组按站点代码排序；同组按 `display_order`、运营姓名排序。
- 上移/下移只调整同站点人员的 `display_order`，统一使用现有批量保存接口持久化。

## 6. 部署与数据安全

- 本次不新增数据库表或 Alembic 迁移。
- 两批都先本地测试和构建，再部署开发环境验收。
- 生产 API 使用新绿色实例健康后热切 Caddy；旧实例保留已有连接。前端单独替换。
- 补数前执行 PostgreSQL 备份；重导后只接受预期新增，核对现有状态和认领记录未变化。
- 生产不得执行 100 并发压测；并发验证放在开发环境。

## 7. 文档同步

实现完成后使用 `neat-freak` 合并更新现行需求、实现状态、架构、运维、源表实测、推进总控、决策记录、README 和交接文档。删除中的旧规格和过期计划不恢复，生产事故事实写入运维和交接文档，不在规则文件重复叙事。

## 8. 验收标准

- 含“月销合计”的合法商品行不再跳过，真正汇总/重复表头仍跳过。
- 上传源表写入 Compose 持久卷目录。
- 所有指定页面显示“认领单销”和实际值。
- 运营可在复核前修改且不会产生重复复核任务；复核后无法修改。
- 运营认领台默认最新期数并可筛选历史和操作状态。
- 商品看板主行直接看到运营。
- 分配台四类筛选可组合，多关键词和运营筛选行为符合口径。
- 运营按站点和自定义顺序稳定展示。
- 后端测试、前端测试、前端构建和生产冒烟全部通过。
