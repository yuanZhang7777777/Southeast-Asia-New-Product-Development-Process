# 运营认领提交状态设计

## 目标

让运营明确区分填写状态，并保持现有“主管复核前可修改、复核后不可修改”的业务规则。

## 状态与文案

- 从未操作：`待填写`。
- 首次填写但未提交，或已提交后再次修改：`已填写未提交`。
- API 提交成功且页面内容未再修改：`已提交`，辅助说明为`待主管复核`。

提交状态放在提交按钮附近。提交按钮首次显示`提交`；已提交内容再次修改时显示`提交修改`。页面不展示“写入数据库”等技术术语。

## 数据边界

- 输入内容只保存在当前浏览器草稿中。
- 单行提交、本组提交和一键提交都会调用现有认领接口；接口成功后才视为已提交。
- 主管复核前再次提交更新同一条认领记录，不新增重复记录或重复复核任务。
- 接口失败时保留草稿并显示失败信息，不将页面误标为已提交。
- 认领 / 不认领往返切换只改变当前模式，不清空另一模式已填的单销或原因。
- 已提交认领记录中的调研图片恢复到编辑器；恢复本身不标记为修改，增删图片才标记`已填写未提交`。
- 选品1源表认领字段仅作原值追溯，不构成平台草稿、提交记录或分配推荐。

## 实现范围

- 复用现有机会状态和最新认领字段判断是否已提交，不新增数据库字段或接口。
- 在公共认领草稿模块增加草稿与已保存值的比较逻辑。
- 列表行与详情矩阵使用相同的提交状态文案。
- 详情成本区域按真实表头过滤选品1源表的`不认领理由 / 主销售员`列，不误伤不同期数中同列号的物流字段。
- 调整通用操作刷新逻辑，避免成功提示被`已刷新`覆盖。

## 验证

- 草稿状态单元测试覆盖待填写、首次填写未提交、已提交、提交后修改。
- 前端完整测试和生产构建通过。
- 生产采用前端候选容器滚动切换，不重启 API、数据库、Redis、worker 或 scheduler。
