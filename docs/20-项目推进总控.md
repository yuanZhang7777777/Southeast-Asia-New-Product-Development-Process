## 4. 下一步执行顺序

### Step 1：新业务平台先行

- 业务指定切入期和首批实际使用人员。
- 切入期后新增 `选品1 / 选品2 / 销售自选` 全部从平台进入；旧 Excel 只作只读参考或接收平台导出。
- 每天核对导入数、分配数、提交数、导出数和异常，不再维护第二套手工状态。
- ERP 凭据未齐前继续使用已验收的手填长宽高降级。

### Step 2：每日历史到货观察与 Item 候选确认

- 每天查看开发试运行日志：08:00 下载前一天 PLM，09:00-23:45 每 15 分钟重试；无命中不发卡，有命中只由刘学城先核对。
- 当前 PLM 销售员是到货通知权威；历史认领人只作来源留痕，不能据此覆盖责任人或创建平台后续任务。
- 按上表三类处理 FineBI 候选：唯一候选先审阅，多候选人工选择，未命中按用户指示暂不处理。
- 两份历史市场监控表继续保持只读：39 组冲突、错误公式和 A:AR 字段合同未裁决前不实现 `apply`。

### Step 3：下一笔正式导出验证 PLM

- 正式导出一条开发记录进入 `waiting_arrival`，等待对应真实 PLM 新到货。
- 写前备份并即时预查，要求计划匹配数恰好为 1；一次性调用现有处理服务，不修改持久开关。
- 验收恰好新增一条到货、一条状态推进和一条审计；同文件重跑必须幂等，通知发送必须为 0。

### Step 4：复用现有周 Item 原始源

- 现有交付包为 `E:\Project\hermes\group8_item_week_package_20260715.zip`；FineBI 原始表 `ItemID财务数据八部` 已含 Item、店铺、订单量、总收入和一次毛利。
- `< 7` 门槛只在现有 `build_item_workbook()` 生成成品表时执行；平台直接读取过滤前原始行，并只聚合正在跟踪的 `Item + 店铺 + 周期`。
- FineBI 原始表能在发生财务行后按主 SKU 提供滞后的店铺 + Item 候选，但没有子 SKU，不能实时发现或证明具体子 SKU 刊登；PLM 和现有 ERP 体积接口也不返回店铺 + Item。未命中记录继续由运营手填。
- 把聚合结果和来源快照接入 `apply_week_metrics(...)`，再补调度、失败重试和监控；不改变集团八部原周报口径。
- 两份市场监控历史表不含上述 Item 周期指标；钉钉 `精品流程` 虽有店铺 + Item，但本次命中记录的四周指标均为空。两者都不能作为四周数据源。

### Step 5：生产发布评估

- 汇总切入期试运行、PLM 精确匹配和开放风险。
- 单独申请非工作时间生产窗口；发布前备份，构建候选容器并验证健康。
- 不在业务使用时段重启生产；PostgreSQL 和 Redis 不随应用发布重建。
