## 4. 下一步执行顺序

### Step 1：新业务平台先行

- 业务指定切入期和首批实际使用人员。
- 切入期后新增 `选品1 / 选品2 / 销售自选` 全部从平台进入；旧 Excel 只作只读参考或接收平台导出。
- 每天核对导入数、分配数、提交数、导出数和异常，不再维护第二套手工状态。
- ERP 凭据未齐前继续使用已验收的手填长宽高降级。

### Step 2：历史数据只读对账

- 匹配键按来源、业务期、标准化站点、主 SKU、子 SKU；责任键再加销售员。
- 规范化只用于匹配，原值、文件、Sheet、行号、行哈希必须保留。
- 只允许完全唯一且平台目标为空的候选进入未来写入清单；39 组冲突不自动决策，公式错误不转换为 0。
- 字段合同和历史状态规则确认前，只交付报告，不实现 `apply`。

### Step 3：下一笔正式导出验证 PLM

- 正式导出一条开发记录进入 `waiting_arrival`，等待对应真实 PLM 新到货。
- 写前备份并即时预查，要求计划匹配数恰好为 1；一次性调用现有处理服务，不修改持久开关。
- 验收恰好新增一条到货、一条状态推进和一条审计；同文件重跑必须幂等，通知发送必须为 0。

### Step 4：接周 Item 真实接口

- 样例必须包含 Item、周四至周三周期、订单量、总收入、一次毛利额，并覆盖低于 7 单、真实 0 和完全缺失 Item。
- 先接只读拉取和来源快照，再接 `apply_week_metrics(...)`、调度、失败重试和监控。
- 两份市场监控历史表不含上述 Item 周期指标，不能作为四周数据源。

### Step 5：生产发布评估

- 汇总切入期试运行、PLM 精确匹配和开放风险。
- 单独申请非工作时间生产窗口；发布前备份，构建候选容器并验证健康。
- 不在业务使用时段重启生产；PostgreSQL 和 Redis 不随应用发布重建。
